About this release [top]

Entrust IdentityGuard Release 12.0 delivers the changes described in this section. 

Attention: Operating system upgrades
If you are performing a major Operating System (OS) upgrade in addition to upgrading Entrust IdentityGuard, you must handle the upgrades separately. For more information, see "Upgrading the OS and Entrust IdentityGuard" in the Entrust IdentityGuard Server Installation Guide.

New features and enhancements [top]

Web-based Java keystore management and alerting (IDG-153)
For installations that use the embedded Tomcat Java application server, this release simplifies the tasks related to managing certificates needed by Entrust IdentityGuard. These tasks include switching from a self-signed to a CA-signed certificate, updating certificates that are nearing expiry, and managing third-party certificates. The feature also warns you when certificates are nearing expiry or have expired.
For more information, see "Managing certificates in the key store" in the Entrust IdentityGuard Server Administration Guide and the Entrust IdentityGuard Self-Service Module Installation and Configuration Guide.
User Access Groups (IDG-156)
For customers that do not have control of LDAP directory settings or who are using a database, this feature allows more options to allow access control to protected resources by group membership. Previously they could use only Entrust IdentityGuard groups. A new User Data policy, Maximum Number of User Access Groups, lets you specify the number of groups that users governed by the policy can belong to, and lets you specify the group names. The policy setting can be overridden for specific users, if required. 
For more information and configuration details, see "Configuring user access groups" in the Entrust IdentityGuard Server Administration Guide.
Send push authentication challenges to mobile soft token and smart credential apps from the Administration interface (IDG-155)
Typically, mobile soft tokens and mobile smart credentials receive authentication challenges from Web sites. This feature allows an Entrust IdentityGuard administrator to send a challenge to a user's mobile soft token or smart credential app on demand from the Administration interface. This way, push authentication can be used in new scenarios, for example, to grant someone access to a building (like a badge) or to verify the identity of someone calling a help desk to reset a password or obtain account information.
For more information and configuration details, see "Push authentication challenges to mobile smart credentials from the Administration interface" in the Entrust IdentityGuard Server Administration Guide.
Anonymous smart credential security challenges (IDG-96)
This feature provides options for users to respond to smart credential security challenges without first entering a user name. In the traditional security challenge feature, users browse to a protected web application, enter their user names and receive push notifications on their mobile devices. With anonymous security challenges, the web application no longer needs to prompt for a user name. Instead, it displays a QR code that the user scans and responds to with the smart credential app (version 3.1 or later). Alternatively, users with physical smart credentials can authenticate  anonymous challenges using Entrust Entelligence Security Provider for Windows (version 10.0 Patch 206124 or later). After responding to the anonymous security challenge, the web application knows which user completed the challenge. This feature requires Entrust IdentityGuard Self-Service Module 12.0 and the Entrust IdentityGuard Mobile Smart Credential app version 3.1.
For more information, see the Entrust IdentityGuard Smart Credentials Guide. 
Enhancements to the detecting risk for adaptive authentication (IDG-149) 
This feature builds on Entrust IdentityGuard 11.0 improvements to adaptive authentication (also known as risk-based authentication). The current device fingerprint solution allows Entrust IdentityGuard to skip second-factor authentication when a user authenticates from the same device. With this release, Entrust IdentityGuard uses device reputation data collected by iovation to track whether that device has been involved in fraud or suspicious activity elsewhere. This integration adds another level of confidence that the user and device requesting authentication are legitimate.
For more information, see the Entrust IdentityGuard Server Administration Guide and the Entrust IdentityGuard Device Fingerprint SDK Programming Guide.
Support for new Entrust Datacard branded hardware tokens (IDG-150)
With release 12.0, Entrust IdentityGuard expands support to a new set of Entrust Datacard hardware tokens comparable to existing Entrust tokens. 
  • Entrust Datacard OT Token: An OATH-compliant, time-based token that is comparable to the Entrust Mini-token OT.
  • Entrust Datacard AT Token (coming soon): An OATH-derivative, event and time hybrid token that is comparable to the Entrust Mini-token AT.
  • Entrust Datacard CR Token (coming soon): An OATH-compliant, time-based token with support for OATH OCRA challenge/response and signature modes. It has a keypad and is PIN-protected. It is comparable to the Entrust Pocket Token and Entrust Flexi Token.
The new Entrust Datacard tokens are supported with the OATH token vendor configuration.
Support for TruCredential for smart card layout (IDG-58)
Datacard TruCredential is the Entrust Datacard card enrollment and layout system. Entrust IdentityGuard makes use of TruCredential smart card design templates and layout editing features for those customers who want to design their own printable smart cards. New Entrust IdentityGuard installations should use Entrust Datacard TruCredential, which is sold, installed, and licensed separately from Entrust IdentityGuard. TruCredential replaces IDWorks (sales to be discontinued by mid-2017) and AlphaCard (for which no new licenses are available). Although IDWorks and AlphaCard will be supported for installed systems, consider switching to TruCredential for next-generation features and long-term support.
For more information, see the Entrust IdentityGuard Smart Credentials Guide and the Entrust IdentityGuard Print Module User Guide. 
Support for issuing Windows TPM virtual smart cards (IDG-933)
This release introduces support for issuing digital IDs to Microsoft Windows virtual smart cards running in the Trusted Platform Module (TPM) hardware available on some Microsoft Windows-based computers. Users derive the new credential from existing smart cards. For more information, see "Derived smart credentials" in the Entrust IdentityGuard Smart Credentials Guide.
Android Mobile Soft Token Samsung KNOX Secure Transfer Activation Mode (IDGM-17)
A new secure transfer activation mode allows Samsung Android devices to import the soft token seed in an encrypted form directly into the Samsung KNOX Trusted Execution Environment (TEE). This feature protects the soft token seed against compromised Android devices during the activation process. This feature requires Entrust IdentityGuard Self-Service Module 12.0, the Entrust IdentityGuard Mobile Soft Token app version 3.2 and a compatible Samsung device.

Changed [top]

Key store requires at least one trusted certificate
With release 12.0 there is a new requirement that there be at least one trusted certificate in the key store. If the last trusted certificate is removed, the Tomcat server will not start. The new Key Store Management interface available in Entrust IdentityGuard installations with embedded Tomcat does not permit deletion of the last trusted certificate. For those installations that use keytool or another key store management tool, you need to be aware of this requirement. If all trusted certificates are removed accidentally, at least one must be re-added to the key store using keytool.
Change to permissions in Smart Credential Print Module role (IDG-1371)
The Smart Credential Print Module role has been updated to have the permission, smartCredentialEnrollmentValuesView enabled by default. The permission is required if an unassigned smart credential is to be used to override enrollment variables when it is assigned to a user smart credential. This is a requirement to support third-party smart cards. If you have administrative accounts with this role that were created in Entrust IdentityGuard 11.0 or earlier, enable the permission if your installation will use third-party smart cards. See "Modify a role" in the Entrust IdentityGuard Server Administration Guide.
Strengthened TLS Server configuration
This release has upgraded the out-of-the-box Apache Tomcat TLS ciphers to use and prefer stronger cipher suites and key sizes.
Filter LDAP users when creating Entrust IdentityGuard user accounts (IDG-201, 204581)
When Entrust IdentityGuard is configured against an LDAP repository, administrators have the option to selectively enroll users that exist in the repository but do not yet have an Entrust IdentityGuard account. This list of users can be large and the administrator must look through many pages to find the intended users. This feature has been enhanced to allow administrators to enter search terms that filter the list of results, allowing them to find the specific users quickly.

Fixed [top]

Properties Editor incorrectly detected changes to eGrid delivery property (IDG-141)
When saving changes or logging out of the Entrust IdentityGuard Properties Editor, the application could incorrectly show that there was a change to an eGrid property (identityguard.user.delivery.smtp.<instance name>.egrid) when validating the page. This issue has been resolved.
Windows upgrade issue when the $identityguard.home/lib/db folder is empty (IDG-715)
Upgrades to Entrust IdentityGuard 11.0 could fail if the $identityguard.home/lib/db folder was empty. This affected only upgrade running against LDAP repositories. This issue is resolved in the upgrade to release 12.0.
Radius server fails to start if secondary authentication types are configured but not used (IDG-2273)
The Entrust IdentityGuard Radius Proxy Server failed to start when a VPN instance was configured for first-factor authentication only but had second factor-authentication types defined. This could occur if the VPN instance was configured for second-factor authentication and  later changed to first-factor only.  This issue has been resolved. Entrust IdentityGuard now ignores the second-factor authentication settings when an instance is configured only for first-factor authentication.
Out-of-band OTP SMS delivery custom class field was not displayed (IDG-2201)
When trying to configure a custom delivery implementation in Entrust IdentityGuard Properties Editor, the field to enter the custom class name was not displayed. This issue has been resolved.
Variables inserted into HTML emails were not escaping special characters properly (IDG-1094)
When trying send emails that substitute variables with special characters such as passwords, the variables were not escaped correctly. This could cause some email clients to display the value incorrectly. This issue has been resolved.
IdentityGuard Radius re-used Radius message IDs too quickly (IDG-312)
In some situations, the Entrust IdentityGuard Radius Proxy server  incorrectly re-used Radius message IDs when communicating with external Radius Servers. This issue could cause the authentication to fail. This issue has been resolved.
Push authentication performance improvement (IDG-101)
HTTPS connections to the Entrust IdentityGuard Self-Service Module Transaction component were not closed during push authentication. When under heavy system load, this could reduce the throughput of push authentication. This issue has been resolved.

Upgrade notes  [top]

Release 12.0 supported only on 64-bit operating systems
Before Release 10.2, Entrust IdentityGuard Server (a Java application) incorporated native 32-bit code and had to run on a 32-bit Java runtime environment, even when running on a 64-bit operating system. All newer installations run on a 64-bit Java runtime environment, and run on 64-bit operating systems only. No 32-bit version is available for upgrades or for new installations.
Supported upgrade paths

Entrust IdentityGuard Server 10.1 11.0, then 12.0
Entrust IdentityGuard Server 10.2 12.0 
Entrust IdentityGuard Server 10.2 FP1 12.0 
Entrust IdentityGuard Server 11.012.0
* In cases where more than one upgrade is required, the second upgrade can be applied immediately after the first. There is no need to run the first upgrade in the production environment before applying the second upgrade.

For full upgrade instructions, see the Entrust IdentityGuard Server Installation Guide.

No LDAP schema update between releases 11.0 and 12.0
If you use an LDAP repository for your Entrust IdentityGuard installation and you are updating from Entrust IdentityGuard 11.0, you do not need to load a new LDIF schema for release 12.0. There have been no LDAP schema updates since the 11.0 release. If you are upgrading from an earlier Entrust IdentityGuard release, follow the instructions for your repository type in the Entrust IdentityGuard Directory Configuration Guide.
Camera Token and Vasco Token plugins
If you are using the Entrust IdentityGuard Camera Token or the Entrust IdentityGuard Vasco Token plugins, you must re-apply the plugins after upgrading to Entrust IdentityGuard 12.0.
Upgrade best practices
  • Before upgrading Entrust IdentityGuard, ensure that you have backed up your Entrust IdentityGuard installation and repository. If using a virtual machine, take a snapshot so you can roll back to it in case of issues. 
  • Ensure that you have sufficient disk space available prior to beginning the upgrade. 
  • On Microsoft Windows servers, rut the upgrade with administrator permissions and, if possible, use the same administrator account used to install the previous version of Entrust IdentityGuard.

Installation, upgrade and configuration  [top]

After upgrade on WebSphere, desktop shortcuts to Entrust IdentityGuard not visible (200655)
After upgrading a WebSphere installation of Entrust IdentityGuard from 10.2 FP1 to 11.0, the start menu shortcuts for the Administration interface and Properties Editor are not visible. To open the Web applications in your Web browser, replace the hostname and port in the following examples and paste them into your Web browser address bar, and then save them as bookmarks or favorites.

https://<hostname>:<port>/IdentityGuardAdmin
https://<hostname>:<port>/IdentityGuardPropertiesEditor 
Port numbers of previous WebLogic installation are used by new WebSphere installation (199818)
A backup configuration from an Entrust IdentityGuard installation with WebLogic does not update the port URLs when the configuration is restored in an Entrust IdentityGuard installation with WebSphere.
Workaround: Update the URLs in the identityguard.properties file to the correct port values after restoring the backup.
If OTP delivery instance name contains a space, backup fails (182922)
Entrust IdentityGuard backup fails if the identityguard.properties file contains OTP delivery configurations in which the instance name contains one or more spaces. To avoid this issue, ensure that the delivery configuration instance names do not contain spaces.
Uninstall leaves folders and files behind (180039)
After uninstalling the Entrust IdentityGuard Server, the root Entrust folder is preserved, along with the Logs and Services sub-folders. The identityguard.properties file is also preserved.
Test Connection in Entrust IdentityGuard post-install configuration fails if the DN contains multiple spaces (182499)
If an LDAP searchbase entered in the IdentityGuard Windows configuration contains multiple consecutive spaces, the verify operation may fail. However, the correct value will be stored in the identityguard.properties file and IdentityGuard will use the correct value to connect to the repository.

Database or directory  [top]

Oracle Internet Directory search issue
An issue has been identified with newer Oracle Internet Directory 11gR1 patches where searches that include binary attributes fail. This has been observed inOracle Internet Directory 11gR1 Patches 7 and Patch 9. The last version that has been confirmed to work correctly is Oracle Internet Directory 11gR1 Patch 2.
Authentication service: Reduced performance if Entrust IdentityGuard schema is fully-indexed
Under high loads, a fully-indexed Entrust IdentityGuard schema may negatively impact the performance of the Authentication service. To optimize the performance of the Authentication service, remove all indexes from the Entrust IdentityGuard schema that do not relate to authentication. For more information on the Entrust IdentityGuard schema, see the Entrust IdentityGuard Directory Configuration Guide.
Note: Removing indexes related to the Administration service may negatively impact the performance of the Administration service.

QR Code image displayed differently in various email clients (195010)
Users can activate soft tokens when offline by scanning a QR code sent in an email message. Depending on the email client used to open the message, the QR code image may not appear as an inline image as expected. Smart credentials  [top]

Windows Smart Card Logon using Windows TPM Virtual Smart Cards (IDG-2331)
Derived credentials issued to Windows TPM virtual smart cards cannot be used for Windows smart card logon using the recommended digital ID configuration shipped with Entrust IdentityGuard 12.0. The virtual smart card can be used for browser mutual authenticated TLS connections and other application-specific uses.
Note: This is being investigated with Microsoft and will be addressed following the 12.0 release.
Issues performing user DN changes against Entrust Authority Security Manager backed by Active Directory Lightweight Directory Servers (AD LDS)  (203413)
When Entrust IdentityGuard is issuing smart credentials from an Entrust Authority Security Manager installed against AD LDS, it may not be able to perform DN change operations successfully.  
Workaround: Using Entrust Authority Security Manager Administration, manually set the user into a DN change state.  Then update the user smart credential in Entrust IdentityGuard and attempt to reissue the credential.
Re-encoding a smart credential fails after changing the PIN policy or after changing the smart credential definition (180325)
An issue occurs if you have a user smart credential with a PIN that is four digits, for example, and then you update the PIN policies (in the smart credential definition) so that the minimum PIN length is longer, say six digits. In this scenario, when you re-encode the smart credential, it will fail because the user PIN has a length is four but the minimum is six. 
Workaround: Update all user smart credential PINs to match the definition requirements before changing the definition. 
Note: This issue is not specific to PINs. It can happen if you change any attributes in the definition, such as making an optional attribute required, or changing the allowed values of a particular attribute. In general, you should avoid changing the smart credential definition after you have created user smart credentials or be aware that you will need to update all user smart credentials so they contain values that match the definition.
Smart credential certificate type must not include uppercase letters (174633)
When you configure smart credentials against an Entrust CA (called Entrust Authority Security Manager), you must specify a certificate type. This certificate type must not include uppercase letters, or else errors will occur when you encode the smart credential.
If you have already specified a certificate type with uppercase letters in it at the CA, ensure that you convert the letters to lowercase when you specify the certificate type in Entrust IdentityGuard.

Digital IDs  [top]

Mobile enrollment SCEP digital ID storage issue (174613)
To enable the mobile enrollment feature, you must create a SCEP P12 file. If you create this file against a Microsoft CA, and you do not specify a file location, the file is stored in a non-obvious location, here:

C:\Users\<logged_in_user>\AppData\Local\VirtualStore\Program Files (x86)\Entrust\IdentityGuard\identityguard120\bin
Mobile enrollment XAP EPF issue (177763)
If you want to enable the mobile enrollment feature against an Entrust CA, you must create a XAP EPF file. If you create this file using Entrust Authority Security Manager Administration against a subordinate CA (as opposed to a root CA), the XAP EPF file will create errors when you try to use it in Entrust IdentityGuard.
Workaround: Create the file using Entrust IdentityGuard's Master User Shell.

Web application server  [top]

Apache Tomcat logs SEVERE errors during service shutdown (171002)
When Entrust IdentityGuard with embedded Tomcat shuts down, Apache Tomcat detects that there are threads running that have not been stopped. The error messages indicate that these threads are likely to cause a memory leak. These error messages are incorrect as Entrust IdentityGuard also shuts down Apache Tomcat. When the Apache Tomcat server stops, these running threads are stopped and all memory released.
TLS connection errors for older Entrust IdentityGuard clients (171002)
In release 12.0, the default configuration for TLS ciphers and key sizes has been strengthened. Some Entrust IdentityGuard clients may not be able to connect using these stronger settings.  
For Java clients, ensure that they are using Java 8. If you are unable to upgrade the client to Java 8, use  the workaround described below.
Several Entrust IdentityGuard products (such as Federation Module 10.2, Entrust IdentityGuard Self-Service 10.2, and Entrust IdentityGuard Print Module 10.2) included previous versions of Java. If running these products against Entrust IdentityGuard 12.0, apply the latest patches to upgrade them to Java 8. 
Workaround:  
  1. Locate the Apache Tomcat server.xml file (<install_directory>/apache-tomcat-8.5.15/conf/server.xml).  
  2. In that file, find each instance of useServerCipherSuitesOrder="true" and change the value to "false".  
  3. Restart Entrust IdentityGuard.

Hardware security module (HSM)  [top]

Hardware security module slot number and password issue (177960)
When initializing Entrust IdentityGuard Server with an HSM, you are asked to choose an HSM slot number (and following that, an HSM password). Sometimes the slot numbers are not displayed consistently in the Entrust IdentityGuard Master User Shell on the primary and replica Entrust IdentityGuard Servers. For example, the primary server might show slot 1 as mapping to HSM serial number #123000, while the replica server might show slot 1 as mapping to HSM serial number to #123001. Since the slots are mixed up, the password you provide for the HSM (which corresponds to the HSM's serial number—not the slot) might be wrong.
Workaround: Prior to initializing Entrust IdentityGuard Server on both the primary and replica servers, determine the HSM slot-to-serial-number mappings. You can do this using your HSM software. For example, if you are using the LunaSA HSM, you would run vtrl verify in LunaSA's console. Once you know the mappings, you can proceed to initialize Entrust IdentityGuard Server on the primary and replica, choosing the appropriate slot number and password.

General  [top]

Scroll bar appears unexpectedly in Properties Editor in Firefox (200843)
When using the Properties Editor in a small Firefox browser window, the dialog box that appears after a Save operation displays a scroll bar but no data window to scroll. 
Workaround: Make the Firefox window larger to have the dialog box display properly.
Null pointer exception error logged if IdentityGuard Server and Federation Module clocks are not synchronized (183090)
SAML login to the Entrust IdentityGuard Administration interface requires that the clocks on the Entrust IdentityGuard Server and the Federation Module server platforms be synchronized. If they are not, administrative users cannot complete SAML authentication to the Administration interface and a NullPointerException error may be logged.
Changes not retained in Properties Editor (181209)
If you make changes in the Properties Editor, and then restart Entrust IdentityGuard Server, your changes might not be saved and you may see the following error in the logs:
[http-bio-8444-exec-2] [WARN ] [IG.SYSTEM.PropertiesEditor.PropertiesEditorServlet] Failed to validate the CSRF Token. Aborting the saving of properties.
To resolve this issue, clear your browser's cache (Shift+F5, or Ctrl-r). This issue will be addressed in an upcoming patch.

Limitations  [top]

This section describes limitations for the current and one previous release of Entrust IdentityGuard Server. For known issues that originated in previous releases but may still apply to the current release, see the online document Entrust IdentityGuard Server Known Issues & Limitations. Also consult the Technotes and Known Issues section of the Entrust TrustedCare Online site for more information and best practices.

Server-side smart credentials are not supported when using Microsoft CA (201239)
Entrust IdentityGuard does not support creating server-side smart credentials issued by a Microsoft CA. 
Distinguished name change is not supported for smart credentials using Microsoft CA (201239)
Entrust IdentityGuard does not support the DN change operation for credentials issued from a Microsoft CA because it does not currently support key archival. 
LDAP Sync Container Mappings properties do not support non-ASCII characters (201211)
This limitation affects only the Properties Editor LDAP Sync Container Mappings properties, which are used with the feature for Active Directory synchronization with an Entrust IdentityGuard database. The properties in this category cannot handle non-ASCII characters and must be converted to RFC2253 format. 
Workaround: Edit the container names. You can use a UTF conversion tool such as the one found at this location: http://macchiato.com/unicode/convert.html. Output should be specified as UTF-8, Base 16.
Unable to encode PIV and PIV-I smart credentials using Microsoft CA (201239)
Entrust IdentityGuard is not able to issue these smart credentials because it does not currently support key archival in MSCA, which is a requirement for PIV and PIV-I credentials. PIV-C is supported using a Microsoft CA which does not require key archival. For PIV and PIV-I credentials, use Entrust CA instead. 
Disabling smart credential expiry notification is not immediately reflected in Self-Service (184299)
If an administrator disables the policy to send notifications to users whose smart credential certificates are nearing expiry, users may still see certificate expiry warnings the next time they log in to Self-Service. The warnings will be visible only until the next time the expiry notification service runs. Policy changes will be read dynamically (and be reflected immediately) in a future release.
English-only user interface and documentation
Entrust IdentityGuard administrative user interfaces and administrative documentation has not been localized for languages other than English. 
No support for Vasco tokens after Entrust IdentityGuard release 9.3
Vasco tokens are not supported on Entrust IdentityGuard 10.0 and later. If you are upgrading from a Vasco-enabled release (release 9.3), existing Vasco tokens will not work. If you are currently using Vasco tokens, and you want to upgrade to a later release, you must delete all assigned and unassigned Vasco tokens before upgrading.

If you intend to issue digital IDs, the following certification authorities (CA) are supported.

  • Entrust Authority Security Manager 8.x
  • Entrust PKI MSO
  • Microsoft Active Directory Certificate Services, referred to as Microsoft CA, on Windows Server 2012, 2012 R2, 2016 
Note: Microsoft CA requires the administrator to run Entrust IdentityGuard on Windows as a privileged user. This release does not include support for Microsoft CA Proxy component (which allows Entrust IdentityGuard to run on a different platform than Microsoft CA).

If you intend to use Entrust Entelligence Security Provider for Windows for encoding of physical smart credentials, the following version is supported.
  • Entrust Entelligence Security Provider for Windows 9.3 or later

Entrust IdentityGuard Radius proxy requirements [back]

Entrust IdentityGuard provides support for a remote access deployment (for example, an IP-SEC VPN or an SSL VPN).

  • First-factor authentication methods include:
    • Entrust IdentityGuard password
    • Radius server
    • LDAP directory
    • Microsoft Windows domain controller (Kerberos authentication)
    • Dynamic password token
    • Out-of-band one-time password (OTP) delivery
  • Second-factor authentication methods include:
    • Dynamic password token
    • Out-of-band one-time password (OTP) delivery
    • Grid card
    • Personal verification number associated with grid, token, or OTP
    • Knowledge-based questions and answers (1 question)
  • IP-Geolocation risk-based authentication is supported with some VPN vendors
  • PAP, CHAP, or MS-CHAP (V1 or V2) password protection protocols

For more information about the Entrust IdentityGuard Radius proxy, see the Entrust IdentityGuard Installation Guide and the Entrust IdentityGuard Server Administration Guide.

For a complete list of supported combinations certified by the Entrust Ready program, see the Entrust Ready pages of the Entrust Web site at http://www.entrust.com/partners/entrustready/identityguard_partners.htm, or the Entrust IdentityGuard integrations page on TrustedCare. For other inquiries, contact Entrust.

In previous releases, the Radius Proxy Configuration Tool was part of the Entrust IdentityGuard Configuration Panel on Windows, and configradius.sh on UNIX and Linux. The Radius Proxy Configuration Tool allowed you to configure the Entrust IdentityGuard Radius proxy, including adding and managing VPN servers to Entrust IdentityGuard. The Radius Proxy Configuration tool was removed from Entrust IdentityGuard in the 10.2 FP1 release. The Entrust IdentityGuard Properties Editor provides a Web-based interface for configuring Entrust IdentityGuard properties, including properties for the Radius proxy, and adding and managing VPN servers in Entrust IdentityGuard. (169266, 174534)

Entrust IdentityGuard API requirements [back]

For details on all of the methods in the APIs refer to the API documentation included with this release.

Entrust IdentityGuard APIs for Java platforms

The Entrust IdentityGuard API for Java platforms is dependent on the third-party libraries, which are provided as part of your Entrust IdentityGuard installation.

These libraries can be found in the $identityguard.home/client/lib directory, where $identityguard.home is typically:

  • on UNIX, /opt/entrust/identityguard120
  • on Windows, C:\Program Files\Entrust\IdentityGuard\IdentityGuard120 

The Entrust IdentityGuard API for Java Platform is compatible with Java 7.

Your Entrust IdentityGuard installation includes a set of zipped HTML files (referred to as Javadocs), IdentityGuardAuthAPIV11.zip and IdentityGuardAdminAPIV11.zip, that explain the Entrust IdentityGuard Java-based authentication and administration APIs. You can locate these files under $identityguard.home/client/doc.

For more information on the Entrust IdentityGuard APIs for the Java Platform, see the Entrust IdentityGuard Programming Guide for the Java Platform.

Entrust IdentityGuard APIs for C# (.NET) 

The Entrust IdentityGuard proxy classes for C# (.NET), as used by the Entrust IdentityGuard Authentication and Administration services, require that you install the .NET 4.0 Platform on a Windows operating system. The Entrust IdentityGuard installation includes HTML files (located under $identityguard.home/client/C#/doc), which provide the information you need for the C# proxy classes (similar to the Javadocs for the Java Platform Authentication and Administration API).

To run the C# sample, refer to the files included in $identityguard.home/client/C#/CSharpSampleReadme.txt, where $identityguard.home is typically C:\Program Files\Entrust\IdentityGuard\identityguard120.

For more information on the Entrust IdentityGuard APIs for the .NET framework, see the Entrust IdentityGuard Programming Guide for the .NET Framework.

  • SC100D, SC200D
  • SC100DLP, SC200DLP
  • SC100C, SC200C

Hardware Security Module (HSM) requirements [back]

Entrust IdentityGuard master keys can be stored on the following HSMs:

  • SafeNet® Luna SA with driver version 4.3, 4.4, 5.0, and 5.1
  • Thales nShield Connect™ with driver version 11.61

The HSM driver must implement the PKCS#11 v2.1 standard.  A 64-bit version of the HSM driver must be installed on every computer that will host an Entrust IdentityGuard server.

Requirements for SafeNet® Luna SA 

  • The 64-bit version of the Luna SA client is required for new installations and upgrades to Entrust IdentityGuard Server release 12.0.
  • If you used the 32-bit version of the Luna SA client with a previous release of Entrust IdentityGuard, when you upgrade to the Entrust IdentityGuard Server release 12.0, you must manually update the location of the Luna SA library. The default location of the 64-bit Luna SA library is:
    • on Linux: /usr/lunasa/lib/libCryptoki2_64.so
    • on Windows: C:\Program Files\LunaSA\cryptoki.dll

Note: In an implementation using the Luna SA 5.0 client, you must add the following value to the <LunaSA_install>\crystiki.ini file: PE1746Enabled=1. If this value is not present, Entrust IdentityGuard cannot be initialized.

Requirements for Thales nShield Connect™ 

  • The 64-bit version of the Thales nShield Connect client is required for new installations of the Entrust IdentityGuard Server.
  • The integration of the Thales nShield Connect HSM with Entrust IdentityGuard is supported on Linux and Windows operating systems.
  • You must install Entrust IdentityGuard before you initialize the Thales HSM. For more information, see the Entrust IdentityGuard Installation Guide.

The mobile enrollment feature supports the creation of digital IDs using any RSA or ECC algorithm that is supported by the mobile device on which it is being used. (168770)
