IdentityGuard Server 12.0 Administration Guide

Registering certificates

There are two ways in which a user certificate can be registered

●       using the administration interface

●       as part of  risk-based authentication.

When the user certificate is assigned in the Administration interface, it can be used for either method of certificate authentication.

When the certificate is assigned to the user by another method, you must load the certificate into Entrust IdentityGuard before it can be used for authentication.

You can load certificates one at a time or in bulk using the Administration interface or the Master user shell. See Creating a bulk file and Data items for certificate bulk operations for information about loading certificates in bulk.

By default, the Certificate Authentication policy Maximum Number of Certificates per User dictates that each user can have a maximum of 10 certificates If you try to assign certificates when the user is already at their maximum, then an error message is returned. You can change the default value in the Policies section of the Administration interface.

User certificates must be globally unique. If you attempt to load a certificate that does not have a unique issuer DN and serial number, Entrust IdentityGuard returns an error message

When you are using risk-based certificate authentication, the user can register a certificate as part of authentication. There are two ways this can happen, as described below.

In the first case, the certificate is included in the challenge request; whether for RBA authentication or another type. The certificate is registered against the user if the user is authenticated successfully. A common scenario for this kind of certificate authentication follows:

●       The user is using client-authenticated SSL to the application.

●       The application uses the user's certificate from the SSL session to perform a risk-based authentication.

●       Because the application does not recognize the certificate—it is not yet registered to the user—the user is presented with an Entrust IdentityGuard challenge.

●       The user answers the challenge.

●       The application returns the user response and the user certificate to Entrust IdentityGuard.

●       Entrust IdentityGuard registers the user certificate to the user.

The certificate can also be registered to a user during the authentication challenge if the following conditions are true:

●       The user authenticated successfully using other RBA components (machine authentication or IP/Geo authentication, for example).

●       A certificate specified as an RBA parameter is valid but not registered.

●       the GenericChallengeParms.registerCertificate flag was specified as true.

In the second RBA mode of registration, the user must have an explicit authenticator available (token, grid, question and answer, or OTP, for example) in order to register new user certificates, and the application performing authentication must be able to handle the challenge.

When registering certificates in the RBA modes, if the maximum number of certificates has been reached (see Maximum Number of Certificates per User), existing user certificates are deleted automatically if the Automatically Delete Old User Certificates policy is set. See Automatically Delete Old User Certificates.

When automatically deleting certificates, certificates are deleted in this order:

●       expired certificates, starting with the least-recently used certificates

●       non-expired certificates, starting with least-recently used certificates

Certificate deletions continue until the number of certificates registered against the user is fewer than the maximum number of certificates allowed. If certificates cannot be deleted, an error is returned.

When registering a user certificate, an error is returned if the user certificate issuer DN and serial number is not globally unique.
