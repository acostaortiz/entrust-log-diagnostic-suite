IdentityGuard Server 13.0 Administration Guide

Transaction policies

These policies are related to transaction authentication features.

Maximum Details per Transaction

Specifies the maximum number of transaction details that can be included in a request. Transaction details are pieces of information like transaction date, transaction value, transaction operation, and so on. This value depends on how many of these details your application includes in the transaction information

This must be a positive integer.

Default: 10

Maximum Queued Transactions

This policy specifies the number of transactions that can be lined up (queued) for a response from a specific soft token user identity. When the number of transactions waiting for the user response is equal to the setting specified here, the queue is full for that soft token identity. It is STRONGLY recommended that you set the queue size large enough that the queue never becomes full. If the queue does become full, however, and a new transaction arrives, Entrust IdentityGuard removes expired transactions from the queue. If that does not free a space for the new transaction (none is expired), Entrust IdentityGuard discards the oldest transaction in the queue.

Note: If a new transaction has the same details as any other queued transaction, the new one replaces the old one without increasing the number of transactions in the queue.

For more information, see Enable transaction queuing.

Default: 1 (Transaction queuing is not used and the new transaction overwrites the first transaction.)

Transaction Lifetime

This policy specifies the transaction lifetime in seconds. The transaction lifetime is the time between the sending of the challenge and the successful authentication.

Set it to Unlimited to have the challenge last an unlimited amount of time.

Set it to a number of seconds to limit the lifetime. With the default behavior, if the transaction is not answered in the lifetime, a new challenge is generated. If transaction queuing is configured (for mobile soft tokens), a new transaction is generated for every challenge.

Default: Unlimited

Transaction Signature Type

Sets the type for the transaction signature.

Possible values:

•  NONE for the unsigned XML transaction receipt.

•  XML for an XML document containing the XML receipt and the XML digital signature.

•  S/MIME for a BASE-64 encoded S/MIME message. The data portion of the S/MIME message is the XML-formatted receipt.

Default: None

Use Dynamic Transaction Linking

This feature provides compliance with European Banking Authority (EBA) Regulatory Technical Standards for Strong Customer Authentication, Article 98 of Directive 2015/2366 (PSD 2) (see Article 5, Dynamic Linking).

This policy applies to one-time passwords delivered out of band for the purposes of transaction verification. It does not apply to OTPs supplied by challenge/response (CR) hardware tokens or Entrust IdentityGuard Mobile Soft Token, whose default designs already comply with the standard.

Set this policy to Yes to generate OTPs that are dynamically linked to specific transactions and that can be used only to confirm those transactions.

For more information, see Enable dynamic linking of OTPs and transaction details

Default: No
