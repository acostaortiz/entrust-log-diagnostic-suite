Out-of-band OTP options

The following sections describe the various options for creating and delivering OTPs.

OTPs delivered out-of-band

Typically, OTPs are conveyed to users using an out-of-band (OOB) delivery mechanism. By bypassing the primary communication channel (the user’s Internet connection) to relay the password to the user, it becomes harder for an attacker or fraud attempt to succeed. This method of authentication is also referred to as OOB authentication.

You can send OTPs to users by email, SMS, or phone message using mechanisms supplied by Entrust IdentityGuard, or you can implement your own delivery mechanism.

Transaction details included in email or SMS

As an additional level of security, Entrust IdentityGuard can include transaction details in email or SMS messages containing OTPs, although this is not required. This allows the user to confirm that the transaction information is correct before entering the OTP in the application to complete the transaction.

Note: Transaction details are not included in voice messages. 

Users can have multiple active OOB OTPs

In the default Entrust IdentityGuard configuration, each user is allowed one OTP. After the OTP is used for authentication, it is deleted and a new OTP is sent using the configured out-of-band delivery method. This scheme is effective in most cases, but delivery may not always be possible if, for example, users often do not have access to their email or if a user’s mobile phone is out-of-range.

To prevent this potential problem, Entrust IdentityGuard has an option allow each user to have several active OTPs at one time. When a user cannot receive an OTP using the configured out-of-band delivery method, that user still has a list of valid OTPs received in advance to use when they cannot receive a text message or email. Each OTP is deleted after it is used.

Related topic: Set policies for out-of-band OTPs

New OTPs generated automatically

There are two choices for how out-of-band OTP generation works.

In the default configuration, an OTP is sent to a user when the challenge is generated. This is effective in most cases, but can be a problem if, for example, users are often in areas with unreliable mobile phone coverage. You can configure Entrust IdentityGuard to deliver one or more OTPs after the user authenticates to ensure access to valid OTPs for subsequent logins.

Note: Voice message delivery of OTPs does not support the delivery of multiple OTPs. If there are multiple OTPs, only the first is delivered.

The behavior of OTP generation is controlled using the OTP Dynamic Refresh Enabled policy. When new OTPs are generated to replenish the user’s list of OTPs, the expiry date of all of the OTPs is set to whichever is greater, the maximum of the new expiry date of the new OTPs or the current expiry date of existing OTPs.

The following sections describe the two possible scenarios, assuming that OTP delivery is enabled. You can also send the OTPs manually, if necessary.

Scenario 1: OTP Dynamic Refresh Enabled=False

Entrust IdentityGuard sends one or more OTPs if the user requires one when an OTP challenge is requested. New OTPs are generated if any one of the following statements is true:

●       The user has used the requisite number of OTPs as defined in the Dynamic OTP Refresh Threshold policy.

●       The Generate New OTP for Every Challenge Request policy is true.

●       Transaction details are required. (For transaction verification, the user might receive more than one OTP because a separate OTP is required to confirm the transaction).

●       The user’s OTPs have expired.

1.      A user initiates an action that prompts an OTP challenge and an OTP is requested.

2.      The number of valid OTPs the user has used is compared to the Dynamic OTP Refresh Threshold policy, and if the user has used the requisite number of OTPs, new OTPs are sent. 

3.      The user authenticates by entering an OTP into the application.

4.      Entrust IdentityGuard deletes the OTP so that it cannot be used again.

Scenario 2: OTP Dynamic Refresh Enabled=True

Entrust IdentityGuard sends one or more OTPs if the user requires them after successful authentication. New OTPs are generated if any one of the following statements is true:

●       The user has no valid OTPs.

●       The user’s OTPs have expired.

●       The user has used the requisite number of OTPs as defined in the Dynamic OTP Refresh Threshold policy.

1.      A user initiates an action that prompts an OTP challenge and an OTP is requested.

2.      The user authenticates by entering an OTP into the application. The user can enter any one of the unused OTPs.

3.      Entrust IdentityGuard deletes the used OTP so that it cannot be used again.

4.      Entrust IdentityGuard replenishes the user’s list of OTPs.

Note: Even when OTP Dynamic Refresh Enabled = True, OTPs might be generated at the time of the authentication challenge, if:

- The application specifies that OTPs are to be delivered.
- New OTPs were generated during the authentication request.
- An older version of the Entrust IdentityGuard API is being used.

Note: This capability is not available if you are using Entrust IdentityGuard Radius OTP first-factor authentication type in Radius proxy and the Generate New OTP for Every Challenge Request policy is set to true.
