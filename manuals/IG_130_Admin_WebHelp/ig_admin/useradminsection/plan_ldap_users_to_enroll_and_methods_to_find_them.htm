IdentityGuard Server 13.0 Administration Guide

Plan LDAP users to enroll and methods to find them

Before you can start the enrollment and synchronization operation, you need to let Entrust IdentityGuard know exactly which users in your LDAP directory you want to enroll. The decisions you make about who in your organization will use Entrust IdentityGuard and where their information resides in your LDAP directory will affect your configuration of the LDAP synchronization feature in Entrust IdentityGuard. The procedures for setting up LDAP synchronization attempt to provide guidance for the various decisions you make in this planning phase.

To understand the discussion that follows, it is helpful to understand the following terms as they are used in this guide:

LDAP directory — This term is used to represent the content of the entire LDAP directory of an organization, sometimes called a directory information tree (DIT). Typically, the DIT contains sub-trees (which can contain further sub-trees) that represent meaningful categories of LDAP objects, and the branches of the tree taper down to leaf nodes, which are containers that have no further levels under them.

Searchbase — This term is used to describe a portion of the LDAP directory where the LDAP users you want to enroll are located. For each searchbase, Entrust IdentityGuard requires a dedicated database and a configuration instance in the Properties Editor properties group LDAP Directory Server Settings. A searchbase could be your whole LDAP directory, a forest of domains, a sub-tree, a leaf node, or several sub-trees and leaf nodes.

Container — For Entrust IdentityGuard purposes, a container is a single level of an LDAP hierarchy that holds users objects. Containers are an important element in planning LDAP synchronization because when there is a change in the LDAP data for a synchronized user, a notification is sent to Entrust IdentityGuard so the user record can be updated in the database. The container is the object that handles notifications. A leaf node is a container. A sub-tree can also be a container, but notifications are sent only for the top level of the sub-tree. To enable notifications for user objects nested further down in a sub-tree, additional configuration is required in Entrust IdentityGuard..

Note: For Microsoft Active Directory, by default, notifications are delivered to one level of containers in the LDAP hierarchy. While this limitation does not apply to all LDAP directories, the same model was used when expanding support of this feature to other LDAP directories.

Searchbases and configuration

Your LDAP directory hierarchy might mirror the hierarchy of your organization. For example, it might reflect operational divisions, or geographical divisions with nested operational divisions, or any other variations. The important thing is to understand where in the hierarchy the users you want to enroll in Entrust IdentityGuard reside so you can find the most effective way to configure enrollment and synchronization to cover them all.

Depending on what you choose as your searchbase or searchbases, your configuration of the following settings for this feature can vary significantly.

●       LDAP Sync Directory instances — Each searchbase you specify requires its own set of property settings. Each searchbase requires an instance in the Properties Editor under LDAP Directory Server Settings/ LDAP Sync Directory Instances.

●       Databases — Each searchbase you specify requires its own associated database. Database configuration is discussed in Configure synchronization with an LDAP directory and Add a database for synchronized LDAP directory data.

Note: If you are using the Entrust IdentityGuard Virtual Appliance Server, only one database can be used, so any configuration with multiple searchbases would not be supported

●       Notifications — By default, the LDAP directory notifies Entrust IdentityGuard of changes for a single level of the LDAP hierarchy. If your searchbases correspond to single containers in the LDAP directory, notifications are sent by default. If you searchbase has several containers with user objects at different levels, you need to configure LDAP Sync Container Mappings to enable notifications. This is accomplished through the Properties Editor by first defining the mappings in the LDAP Sync Container Mappings properties, and then specifying the mappings you want to use with each searchbase in the LDAP Sync Apply Container Mappings property (in LDAP Directory Server Settings).. If you have a searchbase with numerous sub-trees and containers of users, you need to define and apply mappings for each one. This configuration is discussed in Configure synchronization with an LDAP directory.

●       Filtering — If you are able to target LDAP containers that have only user records, you might not have to define filters to screen out ineligible objects, or the filters might be very simple (for example, to screen out non-human administrative accounts). If your searchbase contains multiple types of LDAP objects, you might need to create multiple or more complex filters (for example, to screen out devices, applications, groups and so on) to ensure that you enroll only eligible user objects.  See Create a user synchronization custom static filter.

Further considerations

In addition, if your Entrust IdentityGuard implementation includes users who are not synchronized with an LDAP directory, there are additional considerations. (Your decisions on these points have more to do with your needs as an organization than Entrust IdentityGuard capabilities.)

●       Combine data for new synced users and non-synced users in the same database? If you configure a single searchbase that contains all your corporate users and you would like their synchronized data to be stored in the same database that you use for users accounts created directly in Entrust IdentityGuard (for example, administrative accounts or partner accounts), you can do so.

●       Create new Entrust IdentityGuard groups? Consider whether you want to partition your user community into different Entrust IdentityGuard groups, and if so, what those groups should be. A group can be associated with multiple repositories. For example, perhaps your African and European IT staff come from two different searchbases. Because each searchbase requires its own database, data for these users will be synchronized with two different databases. However, both sets of users can belong to the same Entrust IdentityGuard group (perhaps named IT). The advantage is, you could configure the Entrust IdentityGuard permissions, roles and policies just once to apply to all users in the group, if they have similar roles in the organization.
