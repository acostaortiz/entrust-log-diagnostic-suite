IdentityGuard Server 13.0 Administration Guide

Enable transaction queuing

The transaction queuing feature is intended for organizations whose users are required to hold multiple transactions in the Mobile Soft Token app until a user can respond to them. For example, it could be used by bank loan officers in the loan approval process who receive several transaction challenges in a day and who might need time to perform other process steps before they can confirm each one.

With this feature configured, Entrust IdentityGuard can deliver multiple transactions to a user's mobile soft token app and the user can address them within a configured amount of time. When this feature is not configured, only one transaction delivered to a soft token identity is active at a time (a new one overwrites an older one), and, typically, transactions expire after a short time.

Prerequisites:

●       Entrust IdentityGuard Server 12.0 with Patch 78604 or newer

●       Entrust IdentityGuard Self-Service Module 12.0 with Patch 86284 or newer

●       Entrust IdentityGuard Mobile Soft Token app version 3.5 or newer

The following policy settings are important to making this feature work well for your users:

●       Transaction policy > Maximum Queued Transactions — This setting determines how many transactions can be lined up for action.

●       Token policy > Token Transaction Lifetime — This setting determines how long each transaction is available for response before it expires.

Example policy configuration

A loan officer at AnyBank, Juan, is asked to approve about 15 loans a day. The approval is granted by responding to a transaction challenge sent to his mobile soft token identity that is used only for queued transactions. The transaction challenge is configured to expire after 2 days (Token Transaction Lifetime). The Entrust IdentityGuard administrator configured the system to hold double they typical daily number of transactions in the queue (Maximum Queued Transactions) to accommodate surges of activity. This means that Juan's queue of transactions for this identity could have up to 30 transactions before the expired or oldest ones are deleted to make room for new ones. Ideally, this maximum is never reached and no transactions are deleted before Juan responds to them.

Juan also uses his mobile soft token to authenticate to his VPN application. For security reasons, authentication challenges expire after a short time (for example, 1 minute). This is why he uses a different mobile soft token identity to respond to those soft token challenges. That identity is associated with his other Entrust IdentityGuard user account (in a different group governed by a different policy which allows only brief token transaction lifetimes).

The same mobile soft token app handles both of Juan's soft token identities which he uses for these different purposes.

To enable transaction queuing

1.      Create an Entrust IdentityGuard group for users who will use the transaction queuing feature. See Create a group.

Note: If users in this group will also use the mobile soft token app to authenticate (for example to log in to their computers or to VPN), they will need a separate Entrust IdentityGuard user account to use this feature, because users can have only one Entrust IdentityGuard group and be associated with only one group policy. The Token Transaction Lifetime policy setting for queued transactions will be set to a much longer time than is required for other transaction verification scenarios.

2.      Create a policy for the new group of users. See Create a policy.

3.      Ensure that challenge caching is not enabled. This setting is not enabled by default.

a.      Start the Entrust IdentityGuard Properties Editor.

b.      On the Table of Contents, click Challenge Cache Settings.

c.      Ensure Cache Challenges is set to False.

For more information about this setting, see Challenge Cache Settings.

4.      Apply the Token and Transaction policy settings required for this feature in the policy. The settings control how many items are queued and how long the transactions are valid.

a.      Log in to the Administration interface. (See Log in and out of the Administration interface)

b.      Select Policies on the menu bar.

c.      Find the policy to modify (see Find a policy).

d.      On the View Policy page, click Edit Policy.

e.      From the Policy Category list, select Token.

f.        Set the Token Transaction Lifetime policy to a value that allows users adequate time to review and respond to multiple transactions. By default this policy is set to 300 seconds (5 minutes). For queued transactions, set it to a period of time appropriate to the your process. It could be a typical 8-hour work day (28800 seconds), or, as in the example above, 2 days (172,800 seconds).

g.      Click Save Changes.

h.      From the Policy Category list, select Transaction.

i.        Set the Maximum Queued Transactions policy based on the rate at which the organization creates transactions during peak loads, then consider doubling this value. The aim is to set a value that can accommodate an unusually high volume but is rarely, if ever, reached. This helps ensure that transaction notifications are not removed from the queue before a user has had time to respond to them.

j.        Set the Transaction Lifetime to a value equal to or greater than the one used for Token Transaction Lifetime. Do not leave the default value, Unlimited.

k.      Click Save Changes.

5.      In the Self-Service Module transaction component, configure the transaction cache lifetime by editing the ehcache.xml file. The ehcache.xml file stores transaction details. By default, the ehcache lifetime is 1800 seconds (30 minutes), which might not be long enough to allow users to authenticate and fetch queued transactions. Set the ehcache lifetime to be at least as long as the token transaction lifetime so that the mobile soft token app will be able to fetch the transactions that are still valid in the Entrust IdentityGuard server. To do so, complete the following steps:

a.      On a server where the transaction component is enabled, open ehcache.xml in an XML editor. This file is located in:

–  <$IGSSM_HOME>\identityguardselfservice<version>\instances\ROOT\etc (Windows)

–  $IGSSM_HOME/identityguardselfservice<version>/etc (Linux)

b.      Locate "TransactionCache".

c.      Change the value of timeToLiveSeconds to the value you set for Token Transaction Lifetime in step 4f, or longer.

In the following example, timeToLiveSeconds is changed to 2 days (172,800 seconds).

<cache name="TransactionCache"

           maxElementsInMemory="10000"

           maxElementsOnDisk="10000"

           overflowToDisk="false"

           eternal="false"

           timeToLiveSeconds="172800"

           diskPersistent="true"

           memoryStoreEvictionPolicy="LRU">

d.      Save the file.

e.      If your implementation uses multiple Self-Service Modules and transaction components, you need to replicate this change in the ehcache.xml file for each transaction component installation. Follow the instructions in ehcache.xml itself to configure the file for replication.

6.      Configure your client application that initiates the transaction challenges. See the Entrust IdentityGuard Mobile Soft Token SDK Programming Guide and the Entrust IdentityGuard Programming Guide (Java or .NET version, as required).

Suggestions for you client application:

●       Use callbacks instead of polling: In the Entrust IdentityGuard repository, transactions are not removed from the queue when they are approved; they remain so that your client application can get transaction receipts. Consider using callbacks as an alternative to polling the authentication service for the transaction receipts. Your client application can optionally provide a callback URL when it initiates the transaction.

●       Consider setting priority values on transactions: The Entrust IdentityGuard Authentication API lets you set an integer value to represent the priority of a transaction (1 is highest priority, 9 is lowest priority). Several transactions can have the same priority. Entrust IdentityGuard does not use this priority value, but it is passed to the Self-Service Module transaction component and displayed to the user in the mobile soft token app. To set the priority, add a transaction detail whose name is ENT_IDG_TRANSACTION_QUEUE_PRIORITY and give a value 1 through 9.  See "Online authentication and transaction verification" in the Entrust IdentityGuard Programming Guide.

7.      Advise users how to use queued transactions. See the help in the Mobile Soft Token app or read the Entrust IdentityGuard Mobile Soft Token App User Guide (Android and iOS versions) available through Entrust Trusted Care. If desired, customize procedures in the user guide (Microsoft Word format).
