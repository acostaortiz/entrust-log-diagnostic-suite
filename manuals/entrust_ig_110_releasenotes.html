About release 11.0 [top]

Entrust IdentityGuard 11.0 delivers the changes described in this section. 

Attention: Operating system upgrades
If you are performing a major Operating System (OS) upgrade in addition to upgrading Entrust IdentityGuard, you must handle the upgrades separately. For more information, see "Upgrading the OS and Entrust IdentityGuard" in the Entrust IdentityGuard Server Installation Guide.

New features and enhancements [top]

Synchronization of user accounts in Active Directory and Entrust IdentityGuard databases (197414)
With this release, Entrust IdentityGuard supports synchronization between Microsoft Active Directory user data and Entrust IdentityGuard user data stored in a database. The feature is configured in Entrust IdentityGuard and requires no schema or other changes in the Active Directory environment. 
Users added in Active Directory can be displayed in an enrollment list that an administrator can then use to create Entrust IdentityGuard accounts. User accounts created this way or already existing in Entrust IdentityGuard can then be synchronized with Active Directory. During a synchronization operation, user names, contact information and expired or disabled status in Active Directory can be updated in the Entrust IdentityGuard database. Synchronization can be performed automatically through Active Directory notifications or on demand by an administrator. 
The synchronized user data in the Entrust IdentityGuard database is a copy of what is in Active Directory, however, Entrust IdentityGuard makes real-time calls to Active Directory to validate a user's Active Directory password and obtain user attributes for Entrust IdentityGuard Radius authentication, SAML authentication and during smart credential creation.
Enhancements to risk-based authentication
This release features enhancements to the machine authentication portion of risk-based authentication (RBA). Previously, Entrust IdentityGuard depended on a customer application to deliver a machine nonce and sequence nonce from a user's browser to test whether there was an exact match that would allow machine authentication. Today, many users delete cookies from their browsers, causing machine authentication to fail and forcing them to re-authenticate.
The new Entrust IdentityGuard Device Fingerprint SDK helps you add new data capture capabilities to your client applications to deliver a more comprehensive and flexible "device fingerprint". The device fingerprint is based on a number of attributes of the user's browser, Android device, or iOS device, with allowances for some change in some attributes. Within Entrust IdentityGuard, new Machine Secret policies related to the device fingerprint allow you to specify which collected attributes should be used in the device fingerprint validation, specify the degree of change (if any) allowed for each attribute, and assign each attribute a relative weight based on the potential risk posed by a change in that attribute.
In addition, if you set Machine Secret policies to require use of nonce values, the Device Fingerprint SDK for Web provides that ability to store the machine nonce and sequence nonce to various storage locations to improve their robustness and protect against a user deleting this information when they delete browser cookies. Use of nonce values is optional with this release due to the enhanced device fingerprinting capabilities.
For more information, see the Entrust IdentityGuard Device Fingerprint SDK Programming Guide, and the "Machine authentication" and "Risk-based authentication" sections of the Entrust IdentityGuard Server Administration Guide.
New security policies to control usage of mobile apps on unsecured devices
The Entrust IdentityGuard mobile applications (Entrust IdentityGuard Mobile Smart Credential version 3.0 or later and Entrust IdentityGuard Mobile Soft Token version 3.1 or later) can now optionally be run on unsecured devices, that is, on Android devices that have been rooted or iOS devices that have been jailbroken. New smart credential and token policies in Entrust IdentityGuard support optional use of this feature.
Storage of mobile soft token seed in Trusted Execution Environment (TEE)
The Entrust IdentityGuard Mobile Soft Token version 3.1 introduces the capability to store mobile soft tokens in the isolated hardware of a mobile device. This provides enhanced security for the soft token seed.  A new optional Entrust IdentityGuard Soft Token policy (Mobile Soft Token Trusted Execution Environment) supports this feature. 
Currently, this feature is supported only on Samsung devices that are KNOX-capable, and that have the Samsung OTP Framework 1.1.1 or later. Review the technical specifications of Samsung devices in your user population to determine if you can make use of this feature. 

Use of this feature requires one TEE Storage for Soft Tokens license for each soft token stored in the TEE.

Support for Touch ID on Mobile Smart Credential app
Users of the Entrust IdentityGuard Mobile Smart Credential app (version 3.0 or later) can take advantage of the iOS Touch ID feature instead of a PIN to unlock their smart credentials when authenticating security challenges. A new Smart Credential policy, Mobile Smart Credential Allow Fingerprint Authentication, enables optional support of this feature.  User procedures are documented in the app help and user guide.
Support for external smart credential login to the Administration interface (195552)
Entrust IdentityGuard supports login to the Administration interface with smart credentials. In this release, the feature is enhanced to allow administrators to log in with smart credentials created by a smart credential issuer other than Entrust IdentityGuard. For more information, see "Enable policies for smart credential login" in the Entrust IdentityGuard Server Administration Guide.  
Support for new user data repositories
Entrust IdentityGuard now supports use of UnboundID and CA Directory as user data repositories. For more information, see the Entrust IdentityGuard Directory Configuration Guide.
Support for Entrust OTP Camera Tokens (197872)
Changes to Entrust IdentityGuard Server allow end users to perform hardware token actions using a new customizable Entrust OTP Camera Token. The token has a built-in camera that decodes QR code and then and delivers a one-time password. Token administration actions can be performed through the Administration interface, or by users themselves through a Self-Service Module Web site. This feature requires the Entrust OTP Camera Token Plugin 1.0 be installed on Entrust IdentityGuard Server. For more information, see the guide Entrust OTP Camera Token Administration Guide.
View user activity
On the View Account page in Entrust IdentityGuard Administration interface there is a new feature that allows the administrator to view all audit logs pertaining to the current user.  This allows an administrator to quickly view the changes to the user account and authentication events. To use this feature, the Audits to Database functionality must be enabled.
New Entrust Flexi token support (201158)
With features comparable to the Entrust Pocket Token, the Entrust Flexi token can be branded on the front and back. 
Support for SUSE Linux Enterprise Server
Entrust IdentityGuard server supports SUSE Linux Enterprise Server 12 (64-bit).
Web-based help system for Entrust IdentityGuard
The Entrust IdentityGuard Server Administration Guide now delivered in the Web-based WebHelp format, available through Entrust Trusted Care. This release also introduces a separate WebHelp format guide: the Entrust IdentityGuard Smart Credentials Guide. Information in this guide was previously in the Entrust IdentityGuard Server Administration Guide.

Changed [top]

Changed maximum value for maxTimeSteps (199927)
The change affects tokens using the Entrust token vendor. The maxTimeSteps value specifies a number of 30-second timesteps that Entrust IdentityGuard searches in both the positive and negative directions during a normal authentication operation to find a token response that matches what the user entered. In previous releases, the maximum value for the maxTimeSteps setting for the Entrust token vendor was 255. In Entrust IdentityGuard Server Release 11.0, this maximum value is changed to 120 (1 hour), to match that of other tokens available from Entrust Datacard. If you have tokens that use the Entrust token vendor and you changed the maxTimeSteps value to something greater than 120, you must change it to 120 or less to continue to use the tokens.
Licensing changes
In previous releases of Entrust IdentityGuard, feature-specific licenses were counted for each authenticator created. Entrust IdentityGuard now associates most licenses with a user account so a user can have more than one of a licensed type of authenticator, for example, multiple soft tokens use only one license. This change applies to all license types except Biometrics and the new license type, TEE Storage for Soft Tokens.
MaxMind GeoIP2 Database Support
Entrust IdentityGuard 11.0 now uses the MaxMind GeoIP2 databases for IP Address location lookups. OFIN customers can now obtain the updated MaxMind GeoIP2 databases from the OFIN website. For instructions, see "Get updated IP data files" in the Entrust IdentityGuard Server Administration Guide.
Entrust IdentityGuard Mobile OTP app renamed
The mobile soft token app is now known as Entrust IdentityGuard Mobile Soft Token.

Fixed [top]

This release resolves the following issues.

Duplicated properties entries for encrypted values(201692)
If you chose to encrypt a property value that had not been encrypted before, both encrypted and unencrypted entries were written to the properties file.
Duplicate French and Spanish questions(201578)
Removed duplicate entries for French and Spanish questions for knowledge-based authentication. 
Correction to groups attribute setting (201511)
A groups attribute setting for certain self-administration actions was changed so it was correctly interpreted as meaning the same groups that received the given authenticator during self-registration. 
Mobile soft token name updated in all supported languages(199313)
All references in all supported languages for IdentityGuard Mobile OTP have been changed to IdentityGuard Mobile ST.
Empty reports in the case of duplicate user IDs (192115)
When two users with the same name were added to two different groups, the reporting tools overlooked the group options and produced empty audit list report. This issue is resolved.
Improved user name information in Administration interface (196576)
Added User's Full Name to the Smart Credential Details page to better correlate user information with the "User's Full Name Matches" search field on the User accounts search page.
PIN Unblocking functionality added to derived smart credential template (195567)
The default smart credential configuration provided for derived credentials have the PIN unblock key disabled. When the smart credential was encoded, it did not have an unblock key and therefore the unblock operation was not available. New templates with this feature are added in release 11.0.
Unable to update Entrust IdentityGuard user name for account renamed in Active Directory (189829)
User account names could not be changed successfully in Entrust IdentityGuard LDAP repositories synchronized with Active Directory when the system was set for global username uniqueness. The issue is resolved.
The -import argument of the policy create command did not handle spaces correctly (189819)
In the Master user shell, if a file imported using the -import argument of the policy create command contained spaces, the command resulted in an error. The policy import command now handles escaped characters appropriately.
PVN error audit not always logged when user has multiple tokens (186191)
User errors with entering personal verification numbers (PVN) were not audited consistently. This issue is resolved.
Potential users not enrolled due to paging issue (178266)
This issue was related to the feature for automatically enrolling enterprise LDAP users in an Entrust IdentityGuard LDAP repository (automatically creating Entrust IdentityGuard user accounts). If the enrollment feature encountered enough disabled accounts (not eligible for enrollment) to fill the first page of results, the filter stopped working and no users were enrolled. This issue has been resolved.

Installation, upgrade and configuration  [top]

After upgrade on WebSphere, desktop shortcuts to Entrust IdentityGuard not visible (200655)
After upgrading a WebSphere installation of Entrust IdentityGuard from 10.2 FP1 to 11.0, the start menu shortcuts for the Administration interface and Properties Editor are not visible. To open the Web applications in your Web browser, replace the hostname and port in the following examples and paste them into your Web browser address bar.

https://<hostname>:<port>/IdentityGuardAdmin
https://<hostname>:<port>/IdentityGuardPropertiesEditor 
Port numbers of previous WebLogic installation are used by new WebSphere installation (199818)
A backup configuration from an Entrust IdentityGuard installation with WebLogic does not update the port URLs when the configuration is restored in an Entrust IdentityGuard installation with WebSphere.
Workaround: Update the URLs in the identityguard.properties file to the correct port values after restoring the backup.
If OTP delivery instance name contains a space, backup fails (182922)
Entrust IdentityGuard backup fails if the identityguard.properties file contains OTP delivery configurations in which the instance name contains one or more spaces. To avoid this issue, ensure that the delivery configuration instance names do not contain spaces.
Uninstall leaves folders and files behind (180039)
After uninstalling the Entrust IdentityGuard Server, the root Entrust folder is preserved, along with the Logs and Services sub-folders. The identityguard.properties file is also preserved.
Test Connection in Entrust IdentityGuard post-install configuration fails if the DN contains multiple spaces (182499)
If an LDAP searchbase entered in the IdentityGuard Windows configuration contains multiple consecutive spaces, the verify operation may fail. However, the correct value will be stored in the identityguard.properties file and IdentityGuard will use the correct value to connect to the repository.

Database or directory  [top]

Authentication service: Reduced performance if Entrust IdentityGuard schema is fully-indexed
Under high loads, a fully-indexed Entrust IdentityGuard schema may negatively impact the performance of the Authentication service. To optimize the performance of the Authentication service, remove all indexes from the Entrust IdentityGuard schema that do not relate to authentication. For more information on the Entrust IdentityGuard schema, see the Entrust IdentityGuard Directory Configuration Guide.
Note: Removing indexes related to the Administration service may negatively impact the performance of the Administration service.

Tokens  [top]

QR Code image displayed differently in various email clients (195010)
With Entrust IdentityGuard 10.2 FP1 Patch 194310 and Entrust IdentityGuard Mobile OTP app 3.0, users can activate soft tokens when offline by scanning a QR code sent in an email message. Depending on the email client used to open the message, the QR code image may not appear as an inline image as expected. For example, it might appear twice (as an image and as an attachment) or only as an attachment.

Smart credentials  [top]

Re-encoding a smart credential fails after changing the PIN policy or after changing the smart credential definition (180325)
An issue occurs if you have a user smart credential with a PIN that is four digits, for example, and then you update the PIN policies (in the smart credential definition) so that the minimum PIN length is longer, say six digits. In this scenario, when you re-encode the smart credential, it will fail because the user PIN has a length is four but the minimum is six. 
Workaround: Update all user smart credential PINs to match the definition requirements before changing the definition. 
Note: This issue is not specific to PINs. It can happen if you change any attributes in the definition, such as making an optional attribute required, or changing the allowed values of a particular attribute. In general, you should avoid changing the smart credential definition after you have created user smart credentials or be aware that you will need to update all user smart credentials so they contain values that match the definition.
Smart credential certificate type must not include uppercase letters (174633)
When you configure smart credentials against an Entrust CA (called Entrust Authority Security Manager), you must specify a certificate type. This certificate type must not include uppercase letters, or else errors will occur when you encode the smart credential.
If you have already specified a certificate type with uppercase letters in it at the CA, ensure that you convert the letters to lowercase when you specify the certificate type in Entrust IdentityGuard.

Digital IDs  [top]

Mobile enrollment SCEP digital ID storage issue (174613)
To enable the mobile enrollment feature, you must create a SCEP P12 file. If you create this file against a Microsoft CA, and you do not specify a file location, the file is stored in a non-obvious location, here:

C:\Users\<logged_in_user>\AppData\Local\VirtualStore\Program Files (x86)\Entrust\IdentityGuard\identityguard102\bin
Mobile enrollment XAP EPF issue (177763)
If you want to enable the mobile enrollment feature against an Entrust CA, you must create a XAP EPF file. If you create this file using Entrust Authority Security Manager Administration against a subordinate CA (as opposed to a root CA), the XAP EPF file will create errors when you try to use it in Entrust IdentityGuard.
Workaround: Create the file using Entrust IdentityGuard's Master User Shell.

Web application server  [top]

Apache Tomcat logs SEVERE errors during service shutdown (171002)
When Entrust IdentityGuard with embedded Tomcat shuts down, Apache Tomcat detects that there are threads running that have not been stopped. The error messages indicate that these threads are likely to cause a memory leak. These error messages are incorrect as Entrust IdentityGuard also shuts down Apache Tomcat. When the Apache Tomcat server stops, these running threads are stopped and all memory released.

Hardware security module (HSM)  [top]

Hardware security module slot number and password issue (177960)
When initializing Entrust IdentityGuard Server with an HSM, you are asked to choose an HSM slot number (and following that, an HSM password). Sometimes the slot numbers are not displayed consistently in the Entrust IdentityGuard Master User Shell on the primary and replica Entrust IdentityGuard Servers. For example, the primary server might show slot 1 as mapping to HSM serial number #123000, while the replica server might show slot 1 as mapping to HSM serial number to #123001. Since the slots are mixed up, the password you provide for the HSM (which corresponds to the HSM's serial number—not the slot) might be wrong.
Workaround: Prior to initializing Entrust IdentityGuard Server on both the primary and replica servers, determine the HSM slot-to-serial-number mappings. You can do this using your HSM software. For example, if you are using the LunaSA HSM, you would run vtrl verify in LunaSA's console. Once you know the mappings, you can proceed to initialize Entrust IdentityGuard Server on the primary and replica, choosing the appropriate slot number and password.

General  [top]

Scroll bar appears unexpectedly in Properties Editor in Firefox (200843)
When using the Properties Editor in a small Firefox browser window, the dialog box that appears after a Save operation displays a scroll bar but no data window to scroll. 
Workaround: Make the Firefox window larger to have the dialog box display properly.
Null pointer exception error logged if IdentityGuard Server and Federation Module clocks are not synchronized (183090)
SAML login to the Entrust IdentityGuard Administration interface requires that the clocks on the Entrust IdentityGuard Server and the Federation Module server platforms be synchronized. If they are not, administrative users cannot complete SAML authentication to the Administration interface and a NullPointerException error may be logged.
Changes not retained in Properties Editor (181209)
If you make changes in the Properties Editor, and then restart Entrust IdentityGuard Server, your changes might not be saved and you may see the following error in the logs:
[http-bio-8444-exec-2] [WARN ] [IG.SYSTEM.PropertiesEditor.PropertiesEditorServlet] Failed to validate the CSRF Token. Aborting the saving of properties.
To resolve this issue, clear your browser's cache (Shift+F5, or Ctrl-r). This issue will be addressed in an upcoming patch.

Limitations  [top]

This section describes limitations for the current and one previous release of Entrust IdentityGuard Server. For known issues that originated in previous releases but may still apply to the current release, see the online document Entrust IdentityGuard Server Known Issues & Limitations. Also consult the Technotes and Known Issues section of the Entrust TrustedCare Online site for more information and best practices.

LDAP Sync Container Mappings properties do not support non-ASCII characters (201211)
This limitation affects only the Properties Editor LDAP Sync Container Mappings properties, which are used with the release 11.0 feature for Active Directory synchronization with an Entrust IdentityGuard database. The properties in this category cannot handle non-ASCII characters and must be converted to RFC2253 format. 
Workaround: Edit the container names. You can use a UTF conversion tool such as the one found at this location: http://macchiato.com/unicode/convert.html. Output should be specified as UTF-8, Base 16.
Unable to encode PIV and PIV-I smart credentials using Microsoft CA (201239)
Entrust IdentityGuard is not able to issue these smart credentials because it does not currently support key archival in MSCA, which is a requirement for PIV and PIV-I credentials. PIV-C is supported using a Microsoft CA which does not require key archival. For PIV and PIV-I credentials, use Entrust CA instead. 
Disabling smart credential expiry notification is not immediately reflected in Self-Service (184299)
If an administrator disables the policy to send notifications to users whose smart credential certificates are nearing expiry, users may still see certificate expiry warnings the next time they log in to Self-Service. The warnings will be visible only until the next time the expiry notification service runs. Policy changes will be read dynamically (and be reflected immediately) in a future release.
English-only user interface and documentation
Entrust IdentityGuard administrative user interfaces and administrative documentation has not been localized for languages other than English. 
No support for LDAPS as the Managed CA's LDAP Port
Currently, Entrust IdentityGuard does not support the use of secure LDAP (LDAPS) as the directory protocol when setting up a Managed CA for smart credentials.
No support for Vasco tokens after Entrust IdentityGuard release 9.3
Vasco tokens are not supported on Entrust IdentityGuard 10.0 and later. If you are upgrading from a Vasco-enabled release (release 9.3), existing Vasco tokens will not work. If you are currently using Vasco tokens, and you want to upgrade to a later release, you must delete all assigned and unassigned Vasco tokens before upgrading.

Entrust IdentityGuard Radius proxy requirements [back]

Entrust IdentityGuard provides support for a remote access deployment (for example, an IP-SEC VPN or an SSL VPN).

  • First-factor authentication methods include:
    • Entrust IdentityGuard password
    • Radius server
    • LDAP directory
    • Microsoft Windows domain controller (Kerberos authentication)
    • Dynamic password token
    • Out-of-band one-time password (OTP) delivery
  • Second-factor authentication methods include:
    • Dynamic password token
    • Out-of-band one-time password (OTP) delivery
    • Grid card
    • Personal verification number associated with grid, token, or OTP
    • Knowledge-based questions and answers (1 question)
  • IP-Geolocation risk-based authentication is supported with some VPN vendors
  • PAP, CHAP, or MS-CHAP (V1 or V2) password protection protocols

For more information about the Entrust IdentityGuard Radius proxy, see the Entrust IdentityGuard Installation Guide and the Entrust IdentityGuard Server Administration Guide.

For a complete list of supported combinations certified by the Entrust Ready program, see the Entrust Ready pages of the Entrust Web site at http://www.entrust.com/partners/entrustready/identityguard_partners.htm, or the Entrust IdentityGuard integrations page on TrustedCare. For other inquiries, contact Entrust.

The Radius Proxy Configuration Tool allowed you to configure the Entrust IdentityGuard Radius proxy, including adding and managing VPN servers to Entrust IdentityGuard. The Radius Proxy Configuration tool was removed from Entrust IdentityGuard in the 10.2 FP1 release. The Entrust IdentityGuard Properties Editor provides a Web-based interface for configuring Entrust IdentityGuard properties, including properties for the Radius proxy, and adding and managing VPN servers in Entrust IdentityGuard. Entrust IdentityGuard APIs for Java platforms

The Entrust IdentityGuard API for Java platforms is dependent on the third-party libraries, which are provided as part of your Entrust IdentityGuard installation.

These libraries can be found in the $identityguard.home/client/lib directory, where $identityguard.home is typically:

  • on UNIX, /opt/entrust/identityguard110
  • on Windows, C:\Program Files\Entrust\IdentityGuard\IdentityGuard110 

The Entrust IdentityGuard API for Java Platform is compatible with Java 7.

Your Entrust IdentityGuard installation includes a set of zipped HTML files (referred to as Javadocs), IdentityGuardAuthAPIV10.zip and IdentityGuardAdminAPIV10.zip, that explain the Entrust IdentityGuard Java-based authentication and administration APIs. You can locate these files under $identityguard.home/client/doc.

For more information on the Entrust IdentityGuard APIs for the Java Platform, see the Entrust IdentityGuard Programming Guide for the Java Platform.

Entrust IdentityGuard APIs for C# (.NET) 

The Entrust IdentityGuard proxy classes for C# (.NET), as used by the Entrust IdentityGuard Authentication and Administration services, require that you install the .NET 3.0 Platform on a Windows operating system. The Entrust IdentityGuard installation includes HTML files (located under $identityguard.home/client/C#/doc), which provide the information you need for the C# proxy classes (similar to the Javadocs for the Java Platform Authentication and Administration API).

To run the C# sample, refer to the files included in $identityguard.home/client/C#/CSharpSampleReadme.txt, where $identityguard.home is typically C:\Program Files\Entrust\IdentityGuard\identityguard110.

For more information on the Entrust IdentityGuard APIs for the .NET framework, see the Entrust IdentityGuard Programming Guide for the .NET Framework.

Token requirements [back]

Entrust IdentityGuard supports the following tokens:

  • Entrust (ActivIdentity®) AT tokens
  • Entrust (ActivIdentity) OE tokens
  • Entrust (ActivIdentity) Pocket Tokens
  • Entrust (ActivIdentity) OT Tokens
  • Entrust (Innovative Card Technologies) InCard DisplayCards
  • Entrust soft tokens (Entrust IdentityGuard Mobile and Entrust IdentityGuard Desktop Soft Token applications)
  • Entrust (NagraID®) event-based and time-based display cards
  • Entrust Flexi Tokens
  • Entrust OTP Camera Tokens

Note: Entrust IdentityGuard has passed OATH Certification Profiles for HOTP and TOTP Validation Server version 1.1. Third-party tokens that have passed the OATH Certification Profile for HOTP or TOTP can be used with Entrust IdentityGuard. The PSKC seed file for the tokens must also conform to RFC 6030.

Smart credential card and token requirements [back]

The following Entrust smart credential cards and tokens are supported:

  • SC100D, SC200D
  • SC100DLP, SC200DLP
  • SC100C, SC200C
  • USB SC100, USB SC200

The 200 codes are FIPS validated smart credentials.

For the USB form factor, only the embedded smart card is FIPS validated.

Virtualization software requirements [back]

Entrust IdentityGuard can run in the following virtualization applications:

  • VMWare/ESX
  • Red Hat Enterprise Linux Virtualization 5 (RHEL 5): KVM virtualization mode
  • Windows 2008, 2012 Server Hyper-V
  • Solaris 10, 11 (SPARC) Containers
  • AIX 6.1 or 7.1 LPAR (running AIX 6.1, or 7.1)

Hardware Security Module (HSM) requirements [back]

Entrust IdentityGuard master keys can be stored on the following HSMs:

  • SafeNet® Luna SA with driver version 4.3, 4.4, 5.0, and 5.1
  • Thales nShield Connect™ with driver version 11.61

The HSM driver must implement the PKCS#11 v2.1 standard.  A 64-bit version of the HSM driver must be installed on every computer that will host an Entrust IdentityGuard server.

Requirements for SafeNet® Luna SA 

  • The 64-bit version of the Luna SA client is required for new installations and upgrades to Entrust IdentityGuard Server release 11.0.
  • If you used the 32-bit version of the Luna SA client with a previous release of Entrust IdentityGuard, when you upgrade to the Entrust IdentityGuard Server release 11.0, you must manually update the location of the Luna SA library. The default location of the 64-bit Luna SA library is:
    • on Linux: /usr/lunasa/lib/libCryptoki2_64.so
    • on Windows: C:\Program Files\LunaSA\cryptoki.dll

Note: In an implementation using the Luna SA 5.0 client, you must add the following value to the <LunaSA_install>\crystiki.ini file: PE1746Enabled=1. If this value is not present, Entrust IdentityGuard cannot be initialized.

Requirements for Thales nShield Connect™ 

  • The 64-bit version of the Thales nShield Connect client is required for new installations of the Entrust IdentityGuard Server.
  • The integration of the Thales nShield Connect HSM with Entrust IdentityGuard is supported on Linux and Windows operating systems.
  • You must install Entrust IdentityGuard before you initialize the Thales HSM. For more information, see the Entrust IdentityGuard Installation Guide.

Requirements for mobile enrollment of Digital IDs (certificates) [back]

If you are enabling the mobile enrollment feature, the following mobile device operation systems are supported:

  • Apple® iOS 7.x and newer for smart phones and tablets
  • Android™ OS 4.x and newer for smart phones
  • Android 2.x and newer for tablets
  • BlackBerry® OS 10.x,and newer for smart phones
  • BlackBerry Tablet OS for PlayBook 1.x and newer
  • Windows Phone 8.x (enrollment is supported, however, there is no way to use the digital IDs)

The mobile enrollment feature supports the creation of digital IDs using any RSA or ECC algorithm that is supported by the mobile device on which it is being used. (168770)

Discontinued support in this release [back]

Support for the following platforms and APIs is discontinued in Entrust IdentityGuard Server release 11.0:

  • RedHat Enterprise Linux 5.x
  • Windows Server 2008, 32 bit
  • WebSphere 7.0
  • WebSphere 8.0
  • WebLogic 10g R3
  • IBM DB2 9.5.x
  • Microsoft SQL Server 2008
  • PostgreSQL 8.4
  • Novell e-Directory 8.8.6
  • All 32-bit operating systems
  • V6 and V7 Entrust IdentityGuard APIs

About the Entrust Java Toolkit [top]

The sample application uses the Entrust Authority Security Toolkit for the Java Platform (Entrust Java Toolkit) to encrypt the Sample Administrator's password in the properties file. The Entrust Java Toolkit is licensed separately from Entrust IdentityGuard. If you want your application to use the Java Toolkit, contact Entrust for licensing. (129604)

Similarly, the XMLVerify, SMIMEVerify, and IGCertAuth samples use the Entrust Java Toolkit for crypto functions. To use this functionality in your application, you must license the Entrust Java Toolkit from Entrust.
