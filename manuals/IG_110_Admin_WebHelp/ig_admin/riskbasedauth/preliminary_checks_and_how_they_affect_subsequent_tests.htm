IdentityGuard Server 11.0 Administration Guide

Preliminary checks and how they affect subsequent tests

When a user needs to be authenticated using RBA, Entrust IdentityGuard runs two preliminary IP address checks that determine which (if any) of the IP/Geolocation tests are performed. The preliminary checks are:

●       Expected locations — With this check, Entrust IdentityGuard determines whether the user’s IP is on the expected location list. Based on the results of this check, certain IP/Geolocation tests may or may not be run.

●       Private IP addresses — With this check, Entrust IdentityGuard determines whether the user’s IP is public or private. Based on the results of this check, certain IP/Geolocation tests may or may not be run.

Note: For details on setting up these preliminary tests, see Using the expected IP location list and Using the location history list.

Based on the results of the expected locations and private IP address checks, the following IP/Geolocation tests are run:

●       IP Blacklist — runs only if Entrust IdentityGuard determines that the user’s IP address does not match one of the expected locations. (In other words, the expected locations whitelist applies before the IP address blacklist.)

●       Country Blacklist — runs only if Entrust IdentityGuard determines that the user’s IP address does not match one of the expected locations, and the IP address is public (since only public IP address can belong to a particular country).

●       Location History — runs only if Entrust IdentityGuard determines that the user’s IP address does not match one of the expected locations.

●       Velocity — Runs only  if the user's policy setting Check Velocity is set to yes, and Entrust IdentityGuard determines that the user’s IP address is public. (Private IP addresses are of the form 10.*.*.*, 172.16.0.0 through 172.31.255.255, or 192.168.*.*. Any IP address that is not in this range is considered a public IP address.)

For a case study on how these tests work together, see RBA case study.

Note: You can use all of the test listed here, but you do not have to. If you do not configure a particular component of risk-based authentication, the related test neither passes nor fails, and does not affect whether or not a particular user is authenticated.
