IdentityGuard Server 11.0 Administration Guide

Understanding roles

An administrator is any user who is assigned one or more roles.

Roles control what operations an administrator is allowed to perform, and which users, administrators, or other system objects (cards, tokens and so on) the administrator can perform operations on. Basically, a role is a collection of four lists:

●       A list of permissions. These permissions define what operations the administrator can perform.

●       A list of policies. This list defines what policies the administrator has access to. This is primarily used to control which policies an administrator can modify or delete. Since only highly privileged administrators should be allowed to modify policies, this list is empty for most administrators.

●       A list of groups. This list defines what groups the administrator has access to, and it serves two purposes:

–  Based on their group membership, it restricts what users and other group-related system objects (such as cards and tokens) the administrator can access and perform operations on. For an administrator to operate on any object that is associated with a group, that group must appear on the administrator’s group list.

–  For administrators who have permission to modify and delete groups, this list controls which groups they can modify and delete.

Note: If you set up an administrator role with No Groups, administrators with this role are unable to:
- perform bulk operations,
- perform user-based operations,
- list cards, tokens, or certificates assigned to users
- list or create preproduced cards, or
- list or load unassigned tokens.

These administrators have no group permissions.

●       A list of roles. This list defines what roles the administrator has access to, and it serves two purposes:

–  It controls which administrators can administer other administrators. This allows you to set up roles that permit administrators to administer other administrators (the superuser role is one example). It allows you to set up roles that permit administrators to operate on regular users but not other administrators (the useradmin role is one example). To operate on an administrator, or any of that administrator's data (such as their cards), that administrator's role must appear on this list.

–  For administrators who have permission to modify and delete roles, this list controls which roles they can modify and delete.

Any of these lists can be assigned the special “all” option, which means they grant permission for everything for that particular category. The list of groups can also have the special “own” value (this specifies the group the administrator belongs to).

You build roles by extending what they allow. Adding to any of the four lists in a role always grants the ability to do something more within the system. You cannot add anything to these lists that specifically reduces an ability. To make a role more restrictive, remove items from these lists.

In general, for administrators to perform an operation, their role must meet the following conditions:

●       It must grant the relevant permission. For example, to delete a user, it must grant userDelete permission.

●       The policy, group, and role lists must grant access to the object being operated on.

For example, to perform operations on a user (users are always associated with a group), the role must:

–  grant the relevant permission

–  include the user's group in its list of groups

The effects of roles is a bit more complicated when it comes to performing operations on other administrators (“target” administrators), as administrators have both roles and groups. In this case, the role of the administrator performing the operation (“operation” administrator) must:

●       grant the relevant permission

●       include the target administrator’s group in its list of groups

●       include the target administrator’s role in its list of roles.

The target administrator's group and role do not have to be the same as the operation administrator's group and role.
