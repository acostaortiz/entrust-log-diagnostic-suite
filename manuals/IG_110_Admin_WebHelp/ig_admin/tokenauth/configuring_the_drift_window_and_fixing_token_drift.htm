Instructions

Reset new tokens when they are created or activated

To avoid having token drift issues with new tokens, enable the Reset Token When Token is Created or Activated policy. This policy resets the time or event counter, or both (depending on whether you are using time-based or event-based tokens) on first authentication after the token is assigned to a user (for hardware tokens) or when it is created and activated (for soft tokens).

To configure token policies

Increase the allowable event or clock drift window within which users’ token responses are valid

By default, Entrust IdentityGuard automatically accommodates token event drift of up to 10 events, and clock drift up to 5 minutes. If it is common for your users’ event-based tokens to have the buttons pressed multiple times between authentications, or if it is common for your time-based tokens’ clocks to drift more than 5 minutes from the actual time, then you can set Entrust IdentityGuard to automatically correct for token drift greater than 10 events or 5 minutes. With a larger event or clock window, the need to synchronize tokens is reduced. (For more on synchronization, see the next table cell.)

To configure the size of the drift that is accommodated automatically

Fix token drift by synchronizing the token to the server

By default, if the token event drift exceeds 10 events, or the clock drift exceeds 5 minutes, then the token can no longer be used for authentication. To fix this problem, an administrator can synchronize the token. During a synchronize operation, the token’s event count or clock is synchronized with the one on the Entrust IdentityGuard server.

To fix minor drift by synchronizing the token

Fix token drift that I could not fix through a sync operation

By default, when an administrator synchronizes a token, Entrust IdentityGuard searches 100 future events, or 15 minutes in the past to 1 hour into the future of the current time to find a token response that matches what the user entered. If the drift exceeds these amounts, the Synchronize Token operation does not work.

To fix this problem, you have two options:

·      Option 1: Increase the window of time or the number of events that Entrust IdentityGuard searches during a synchronize operation, and then try the synchronize operation again (this option works for tokens and soft tokens).

·      Option 2: Delete the token and create a new one (this option works for soft tokens only).

For Option 1, see To fix large drift by increasing the size of the event or clock window.

For Option 2, see Delete a token.

 

To configure the size of the drift that is accommodated automatically

1.      Find the entrusttoken.conf file (or an equivalent file with a different name). If the file does not exist, create it as a text file. The default location is:

●       on UNIX, $IG_HOME/etc/

●       on Microsoft Windows, <$IG_HOME>\etc\

2.      Add one of the following entries to the file:

If you are synchronizing...

Add...

Event-based tokens

automaticResetEventWindow=<size>

where <size> is the number of token responses that Entrust IdentityGuard searches during a normal authentication operation to find a token response that matches what the user entered.

Rules for allowable <size> values:

·      must be an integer divisible by 10

·      minimum 10, maximum 200

·      must be smaller than the value set in the resetEventWindow parameter

automaticResetEventWindow=50

The default is 10.

The larger the event window, the greater the risk of someone being able to guess the dynamic token password. Larger event windows can also make authentication slower.

Time-based tokens

maxTimeSteps=<timestep>

where <timestep> is a number of 30-second timesteps that Entrust IdentityGuard searches in both the positive and negative direction during a normal authentication operation to find a token response that matches what the user entered.

One timestep = 30 seconds.

Examples:

maxTimeSteps=10 (10 X 30 = 300 seconds = 5 minutes)
maxTimeSteps=120 (120 X 30 = 3600 seconds = 1 hour)

The default is 10 (5 minutes).

The maximum is 1200 (10 hours).

As the clock window is set larger, the risk of someone being able to guess the dynamic token password increases.

Exactly how long a response is valid depends on how much of the time window had elapsed the last time the user authenticated. Therefore, a token response can be said to be valid for at least maxTimeSteps X 30 and at most (maxTimeSteps + 1) X 30.

3.      Save the file.

To fix minor drift by synchronizing the token

1.      Log in to the Administration interface (Logging in and out of the Administration interface).

2.      Locate the problem token in one of two ways:

●       Find a user’s token

See To find a user’s token information .

●       Find an assigned token

See To search for assigned token information .

3.      After you locate the token in the Administration interface, click Synchronize Token. What happens next depends on the token’s vendor and type.

For some tokens, clicking Synchronize Token is all that is needed. In this case, a confirmation message appears.

In other cases, the Synchronize Token page appears.

4.      If the Synchronize a user’s Token page appears, enter the required responses. Depending on the token vendor and type, the page asks for one or two token responses. If you are unsure how many responses to enter, first try with just one response.

●       When one response is required, generate and enter a token password in the Response 1 field.

●       When one response is asked for but is optional, you can either enter the response in the Response 1 field, or leave the field blank. If you leave the field blank, the attempt to synchronize will be made the next time the user authenticates.

●       When two responses are required, enter two token passwords generated in succession in the Response 1 and Response 2 fields.

5.      Click Synchronize Token.

The Token Details or Account Information page reappears. A message at the top informs you if the synchronization operation succeeded or failed.

Note: Hardware and software OT tokens do not behave the same way when reset. When a software OT token is reset, the drift time is reduced to zero. When a hardware OT token is reset, the drift time is reduced by half. If the time drift is big enough, it might require more than one reset to synchronize the hardware OT token.

If this procedure does not fix the problem, see To fix large drift by increasing the size of the event or clock window.

The following procedure help you correct drift if the above procedure is not successful in synchronizing the token.

To fix large drift by increasing the size of the event or clock window

1.      Find the entrusttoken.conf file (or an equivalent file with a different name). If the file does not exist, create it as a text file. The default location is:

●       on UNIX, $IG_HOME/etc/

●       on Microsoft Windows, <$IG_HOME>\etc\

2.      Add one of the following entries to the file:

If you are synchronizing...

Add...

Event-based tokens including

·      Entrust Mini-token AT (time and event)

·      Entrust Pocket Token 

resetEventWindow=<size>

where <size> is the number of token responses that Entrust IdentityGuard searches during a token synchronization in order to find a token response that matches what the user entered. The number must be an integer divisible by 10, for example:

resetEventWindow=200

The default is 100. This means that administrators with the appropriate privileges are able to synchronize tokens for which the event window has gone out of sync by fewer than 100 events.

The minimum is 10. There is no maximum.

Increase the resetEventWindow parameter incrementally and with care. As you increase its value, you also increase the likelihood of a random value accidentally matching.

Entrust time-based OT tokens including

soft tokens in Entrust IdentityGuard Desktop Soft Token application or the Entrust IdentityGuard Mobile ST app

·      Entrust Mini-token OT (time only)

·      Entrust Pocket Token

maxResetTimeSteps=<timestep>

where <timestep> is a number of timesteps that Entrust IdentityGuard searches in both the positive and negative direction during a synchronization operation in order to find a token response that matches what the user entered.

One timestep = 30 seconds.

Examples:

maxResetTimeSteps=120 (60 minutes)
maxResetTimeSteps=60 (30 minutes)

The default is 120 (60 minutes).

There is no minimum. The maximum is 1200 (10 hours).

Increase the maxResetTimeSteps parameter incrementally and with care. As you increase its value, you also increase the likelihood of a random value accidentally matching.

Time-based tokens including

·      Entrust Mini-token AT (time and event)

·      Entrust Mini-token OT (time only)

·      Entrust Pocket Token

resetClockWindow=<minutes>

where <minutes> is the number of minutes that Entrust IdentityGuard searches during a token synchronization in order to find a token response that matches what the user entered.

Example:

resetClockWindow=60

The default is 60. This means that administrators with the appropriate privileges are able to reset tokens for which the clock has gone out-of-sync by less than 60 minutes in the positive or negative direction.

There is no minimum or maximum.

Increase the resetClockWindow parameter incrementally and with care. As you increase its value, you also increase the likelihood of a random value accidentally matching.

3.      Save the file.

4.      Make sure the configuration file is assigned to the token vendor in the Properties Editor.

Follow the procedure at To ensure that the token configuration file is assigned.

5.      Log in to the Administration interface and synchronize the token. (See To fix minor drift by synchronizing the token.)

6.      If this procedure does not correct the problem, edit entrusttoken.conf with a larger value for resetEventWindow or maxResetTimeSteps and synchronize again.

7.      Restore the settings in the entrusttoken.conf file to their original values after synchronizing the tokens.
