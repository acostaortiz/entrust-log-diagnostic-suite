IdentityGuard Server 11.0 Administration Guide

Administering shared secrets

Shared secrets are small bits of information that a client application can release to a user after that user has successfully authenticated. For example, a shared secret can be a pre-assigned access code to an application outside of Entrust IdentityGuard's control. Alternatively, you can just use shared secrets to associate bits of data with the user for administrative purposes.

For example, Entrust IdentityGuard Desktop for Microsoft Windows uses shared secret information to store the offline temporary PIN.

Note: Entrust IdentityGuard uses shared secrets to record a variety of different settings, including whether a user has registered.

Shared secrets are stored in encrypted form in the repository. A client application can retrieve them using the Authentication API, (if the flag allows it), or the Administration API.

Your application can store multiple shared secrets for each user. To configure how many shared secrets a user can have, see Configure shared secret policies.

When creating users, you can assign them shared secret values that your client applications can retrieve and use.

Note: If your organization requires more protection of shared secrets, enable SSL to protect the communication between the Entrust IdentityGuard server and your client application. The client application is responsible for encoding and decoding the shared secret values into string form (for example, Base 64 or HEX encoding).

While you can administer shared secrets, they are not used by Entrust IdentityGuard and do not need to be visible to administrators. Administrators can view shared secrets when their role includes the userGetSecret permission. Administrators need a role with the userSetSecret permission to change or delete a shared secret.

Any changes made to a shared secret take effect the next time they are used for authentication or accessed through the Administration API.
